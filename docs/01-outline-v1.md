> **状态（2026-11-23）**：命题已定稿；实证已跑完并写成 [04-results-v1.md](04-results-v1.md)。本文的"必须回答的问题"清单仍然有效，但 §4 的写法已被实证结果修正——**先读 04，再按本文的节结构落笔**。实证显示原命题需要三处修正（共享端点而非共享层、|E| 随硬件家族增长、门槛看 N 与 M 的绝对规模），修正后的表述见 04 的「对命题的净修正」。

**工作标题**：MLIR 的多级抽象设计及其在 AI 编译器生态中的角色——从成对适配到分层共享的复用成本分析

**核心命题（B 版，已被数据修正为下面这句）**
> MLIR 的核心贡献是把"抽象层级"从编译器的固定架构决策，变成可扩展、可共存的一等对象（dialect / interface / progressive lowering）。这使框架与硬件之间的适配成本从 `N·M` 重写为 `|E| + N + M`，其中 `|E|` 不随层数增长，而随**硬件家族数**及其**内部级数**增长。因此"塌缩"在架构层几乎立即发生，在工程层则需要前端数量超过十余个才划算，且对共享层采纳率 p 高度敏感。

**禁止出现的主张**（评阅人一查就破）
- ❌ "MLIR 解决了 N×M 问题"
- ❌ "MLIR 比 TVM / XLA 更好"
- ❌ "79% 的转换落到硬件目标层"（这个数字依赖层划分，换划分跌到 36.6%，见 04 的稳健性一节）
- ✅ 只允许："在 MLIR 中，X 机制使得 Y 的成本结构从 A 变为 B，证据是 Z"
- ✅ 方言级表述是安全的："101 个转换文件、来自 18 个方言，汇入 `llvm`"

## §3 MLIR 的机制 —— 只讲撑论点的四个机制

**不要**写"MLIR 有哪些 dialect"的清单。评审看的是机制，不是目录。四个机制各对应一个论点：

1. **dialect = 可扩展的算子/类型/属性集合 + 可定制的 verification 与 canonicalization**
   → 论点：抽象的"层级"从编译器内核里被搬到库和模块边界上，于是新增一层不需要改内核。
2. **多级 IR 共存于同一 module + partial lowering**
   → 论点：这是"渐进下降"的前提。若层级不能共存，就仍然只能整段一次性翻译，"分层"就退化为"分阶段流水线"。
   → 配图 2：从真实 IR 里截一段"同一函数体内 linalg + scf + arith + memref 并存"的片段并标注。
3. **op interface（而非仅命名空间）**
   → 论点：**这是 N+M 可加性的技术根源**。pass 通过 interface 对"它未知的 dialect"仍然生效，因此一条转换不必重写。这一点很多人写不出来，写到了就是深度。
4. **conversion target / legality / type converter 的显式语义边界**
   → 论点：层与层之间的边界是可声明的契约（而不是隐式约定），使"边界"本身成为可被检验的对象。

**反面必须提一句**：progressive lowering 的代价是"同一条链上 pass 顺序敏感、调试面变大"，这句为 §6 埋伏笔。

## §6 代价、局限与威胁效度

> **素材已备**：[08-section6-limitations.md](08-section6-limitations.md) 有机制代价四条、局限表（逐条绑定到被削弱的结论）、结论强度分级与数字自检清单。

必须覆盖（每条 3–5 句，别展开成小论文）：
1. **方言碎片化**：共享层之外的私有 dialect 使栈顶仍然每家用一套（这是 RQ2 的反面）。
2. **抽象泄漏**：bufferization、shape 推断、量化是层级之间最难对齐的语义。
3. **IR 膨胀与编译时间**：多级 IR 与 pass 数增加带来的工程成本。
4. **治理成本**：共享层的版本与兼容承诺。
5. **方法局限**：语料代表性、README/测试文件与生产使用的差距、层划分的主观性、`builtin` 被显著低估（见 `meta.json`）。
