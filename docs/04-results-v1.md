> 数据：`llvm-project` @ `ba73617208d4f1621b70173b6088a11c90df91af`，`mlir/test/**` 共 **3,329** 个 `.mlir`，计入 **181,326** 个算子。
> 原始数字见 [out/facts.md](../out/facts.md)（脚本生成，不含解释）；图表见 `out/fig1..fig4.svg`。
> 换算口径：452 个 `Conversion/` 测试文件中 **371 个（82.1%）** 能解析出确定的层间边，其余 81 个是源/目标不定的泛化目录（`ConvertToSPIRV`、`RaiseWasm` 等），只在需要处单独说明。

## 发现 1｜收敛发生在「端点」，而不是「层」

**观察**

- 落到硬件目标层的转换文件占全部层间转换的 **79.0%**（230 / 291）。
- 但真正的汇聚点是三个**具体方言**，而不是"目标层"这个类别：

| 目标方言 | 文件数 |
|---|---|
| `llvm` | 101 |
| `spirv` | 57 |
| `rocdl` | 56 |
| `xevm` | 23 |
| `emitc` | 19 |
| `nvvm` | 19 |

- 汇入 `llvm` 的 101 个文件来自 **18 个不同方言**：`spirv`(25)、`func`(13)、`memref`(10)、`acc`(10)、`vector`(10)、`xevm`(6)、`arith`(5)、`arm_sme`(3)、`async`(3)、`complex`(3)、`cf`(3)、`nvvm`(2)、`omp`(2)、`ptr`(2)、`index`(1)、`math`(1)、`mpi`(1)、`ub`(1)。

**解释**

MLIR 生态里确实存在"多方汇入同一点"的结构，但那个点是 **LLVM dialect**（其次是 SPIR-V / ROCDL），不是某个抽象层。原因不难理解：`llvm` 方言下面直接就是 LLVM 后端，是所有目标里唯一"已经被全行业接受"的接口；SPIR-V 是 GPU 侧的同类接口。

这修正了"分层共享"的直觉图像：共享不是发生在**层与层之间**的对称交换，而是发生在**所有源都指向少数终端**的星形结构上。图 1 里那束汇入右下角的粗线就是它。

**不能说明什么**：这不代表其他层没有价值——`linalg`、`scf`、`memref` 是**变换发生的场所**，只是它们不是**汇聚的场所**。两者是不同的问题。

> 图 1（`fig1_layer_transitions.svg`）承载这条发现；表 `facts.md` §2 是它的数字版。

## 发现 2｜目标层内部有 114 个转换文件、8 条边——「厂商内二级栈」

**观察**（`target` → `target` 的内部转换，共 114 个文件）

| 转换 | 文件数 | 性质 |
|---|---|---|
| `amdgpu` → `rocdl` | 42 | 厂商内：高层 GPU 方言 → 厂商低层方言 |
| `spirv` → `llvm` | 25 | 跨厂商：通用 GPU 出口 → 通用 CPU 出口 |
| `xegpu` → `xevm` | 20 | 厂商内：Intel 高层 → Intel 低层 |
| `acc` → `llvm` | 10 | 出口转向 |
| `nvgpu` → `nvvm` | 6 | 厂商内：NVIDIA 高层 → NVIDIA 低层 |
| `xevm` → `llvm` | 6 | 出口转向 |
| `arm_sme` → `llvm` | 3 | 出口转向 |
| `nvvm` → `llvm` | 2 | 出口转向 |

**解释**

这 114 个文件是全部层间转换中最大的一块，而它们被我原先的 5 层划分**全部折叠进了同一层**，因此层的划分在结构上丢掉了信息。它们实际分成两类：

1. **厂商内二级栈**（`amdgpu→rocdl`、`xegpu→xevm`、`nvgpu→nvvm`，共 68 个文件）：每个硬件厂商在 MLIR 里都不是一层，而是**两级**——一个面向编程模型的方言 + 一个面向指令的方言。
2. **出口转向**（`spirv→llvm`、`acc→llvm`、`xevm→llvm`、`arm_sme→llvm`、`nvvm→llvm`，共 46 个文件）：各种高层目标方言最终都再落到 `llvm`。

**这条发现最有价值的地方**：它说明 MLIR 的转换成本不是按"抽象层数"线性增长的，而是按 **硬件家族数 × 每家族内部级数** 增长的。5 层模型给出的 14 个层边界，严重低估了实际要写的转换数量（79 个方言对），原因正是厂商在目标层内部又各自展开了子栈。

> 图 1 中五个"层内 N"的小凸起就是这条发现；`facts.md` §3 的下半张表是它的明细。

## 发现 3｜投入分布是「四高一起、前端独低」

**观察**（`test/Dialect/<X>` 的文件数，已归属 1,077 个）

| 层 | 文件数 | 占已归属 |
|---|---|---|
| 硬件目标层 | 259 | 24.0% |
| 并行与控制抽象层 | 235 | 21.8% |
| 张量代数/结构化计算层 | 232 | 21.5% |
| 存储与向量层 | 222 | 20.6% |
| 跨层通用方言（单列） | 73 | 6.8% |
| **框架/算子集导入层** | **56** | **5.2%** |

**解释**

四个中后段层的投入几乎均匀（20.6%–24.0%，彼此差不到 4 个百分点），而**框架/算子集导入层的投入只有它们的约 1/4**。含义有两层：

1. 上游对"把框架接进来"这件事投入最少——因为这部分由**别的仓库**承担：`torch-mlir` 承接 PyTorch，`StableHLO` 承接 JAX/TF，`ONNX-MLIR` 承接 ONNX。本语料里 `frontend` 层作为转换源的方言只有 `tosa`（外加极少量 `ml_program`），`torch` / `stablehlo` / `mhlo` 一个都没出现。这是"职责在仓库边界上被切分"的直接证据。
2. 这正是"栈顶碎片化"的量化形态：**复用（=投入）集中在中后段，前端由各生态自己承担**。

**不能说明什么**：投入 ≠ 难度 ≠ 价值。上游测试少也可能只是"导入层的正确性容易由生成器覆盖"。

## 发现 4｜「N×M 塌缩」有两种口径，答案相反

这是全文最关键的一段，也是把 B 版命题真正钉死的地方。

**观察**

| 口径 | 计数对象 | 数量 | p=0.6 时的 N\* |
|---|---|---|---|
| 架构级 | 层与层之间的非零边界 | **14** | **7.7** |
| 工程级 | 真正要写的 (源方言, 目标方言) 对 | **79** | **22.9** |

（`N* = (|E| + M) / (p·M − 1)`，M = 8，即 `target` 层内被作为转换目标的方言数，由数据实测。）

在 N = 8、M = 8 的现实规模下：

- 架构级口径：成对适配 48，分层共享 47.2 → **基本打平**；
- 工程级口径：成对适配 48，分层共享 112.2 → **分层反而更贵**。

**解释**

同一个命题，换个计数单位就从"成立"变成"不成立"。差别不在 p，而在于**你把什么算作"一次实现"**：

- 若认为"增加一层"就是把这一层写一遍，那么层数少（14），共享的收益立刻兑现；
- 若认为"增加一层"实际意味着"给这一层里的每个方言对写一条转换"，那么成本是 79，且它随**硬件家族数**增长，而非随层数增长。

真实工程介于两者之间，但**明显偏向工程级**：`AMDGPUToROCDL` 和 `NVIDIA NVGPUToNVVM` 不可能因为"都在目标层"就被同一条代码实现。

**所以命题必须改写成这个形式才站得住**：

> MLIR 把成本从 `N·M` 重写为 `|E| + N + M`，其中 `|E|` 不随层数 L 增长，而随**硬件家族数**及其**内部级数**增长。因此"塌缩"在架构层（L 小）几乎立即发生，在工程层（|E| 大）则需要前端数量 N 超过十余个才划算；且这一门槛对共享层采纳率 p 高度敏感——p 从 0.8 降到 0.4，N\* 从 16.1 升到 39.6（约 2.5 倍）。

**敏感性数据**（M = 8）

| p | 0.4 | 0.5 | 0.6 | 0.8 | 1.0 |
|---|---|---|---|---|---|
| N\* | 39.6 | 29.0 | 22.9 | 16.1 | 12.4 |

## 发现 5｜`func` / `arith` 是唯一的真·跨层通用语

**观察**（共现矩阵，`fig2`）

- `func` 与 `arith` 的共现文件数 **1,454**，各自与 `memref`(609/562)、`vector`(479/437)、`linalg`(452/379)、`scf`(449/421)、`tensor`(398/353) 的共现都在数百量级。
- `transform` 与 `linalg`(154)、`tensor`(99)、`scf`(62) 的共现显著高于它与其他方言的共现，与 `llvm` 只有 4。
- `llvm` 与 `omp` 共现 **234**，是它除 `func`/`arith` 之外最高的一个。

**解释**

- `func`/`arith` 与几乎所有层都共现，印证它们作为"跨层通用语"的地位：任何层的测试都需要函数外壳和算术原语。这也解释了为什么把它们放进任何单一层都是错的——本实验把它们单列为 `crosslayer` 是对的。
- `transform` 几乎只与结构化计算层共现，说明调度 DSL 是**依附于 `linalg`/`tensor` 的**，而不是独立一层。这为 §3 论证"接口使变换可复用"提供了一个侧证：变换作用点集中，才有可能做成可复用的 transform op。
- `llvm`↔`omp` 的高共现来自 `OpenMPToLLVM` 这条路径，说明并行抽象与通用出口之间存在一条直接的通道。

**不能说明什么**：共现高不等于依赖强；测试文件的粒度不均会放大数值。

## 对命题的净修正

原命题 B 版说"成本从成对定制变为分层共享，收益取决于共享层是否被采纳"。数据支持这个骨架，但要求三处修正：

1. **"共享层"应改为"共享端点"**。数据显示收敛点是 `llvm`（101/18 个来源）、`spirv`、`rocdl`，是点不是层。
2. **"每层一次实现"应改为"每个方言对一次实现"，且 |E| 随硬件家族数与厂商内级数增长**。这是 |E| 从 14 跳到 79 的原因。
3. **收益的门槛不只是 p，还有 N 与 M 的绝对规模**。架构级门槛约 8 个前端，工程级门槛约 12–23 个前端；而现实中的 AI 框架数量正好落在这个门槛附近——这解释了为什么 MLIR 在 2020–2023 年被广泛采纳，而更早的单层 IR 方案没有。

## 稳健性检验｜换一套层划分，哪些结论会变

把主划分的「硬件目标层」拆成 **通用出口层**（`llvm`、`spirv`）+ **厂商指令方言层**（`rocdl`/`amdgpu`/`nvvm`/`nvgpu`/`xegpu`/`xevm`/`arm_*`/`x86`/`wasmssa`/`acc`/`vcix`），层数 5 → 6，重跑全部统计（`tools/layers_alt.json`，输出在 `out_alt/`）。

| 量 | 主划分（5 层） | 替代划分（6 层） | 结论 |
|---|---|---|---|
| 方言对 \|E\| | 79 | **79** | **完全不变**（\|E\| 只由语料决定，与层划分无关） |
| 非零层对 | 14 | 18 | 变 |
| 架构级 N\*（p=0.6, M=8） | 7.7 | 6.8 | 小幅变 |
| 工程级 N\*（p=0.6, M=8） | 22.9 | **22.9** | **完全不变** |
| "落到最深层"的边占比 | 79.0%（target） | 36.4%（vendor） | **大幅变**（这一指标本身依赖划分，不宜单独引用） |
| 四个中段层投入 | 222–235 | 222–235 | 不变 |
| frontend 投入 | 56（5.2%） | 56（5.2%） | 不变 |
| 入度最高的单一方言 | `llvm` 101 | `llvm` 101 | 不变 |

**怎么用这个结果**

- 发现 4 的核心量（`|E| = 79` 与工程级 N\*）**与层划分无关**，因此那条结论是稳的，可以直接写进正文。
- "79% 落到最深层"这个数字**依赖把 `target` 划成一层**，换划分就掉到 36.4%。所以正文**不要单独引用这个百分比**，应改用「101 个转换文件、来自 18 个方言汇入 `llvm`」这种**方言级**表述——后者两种划分下都一样。
- 发现 2（厂商内二级栈）在替代划分里被显式表达为 `vendor→vendor 68` 与 `vendor→generic_exit 21`，与主划分下"target 内部 114 个文件"是同一现象的不同切法，互为印证。

## 必须写进局限的四条

1. **语料是上游测试集**，反映的是"上游维护者认为需要覆盖什么"，不等于工业使用分布；GPU 厂商（AMD/Intel/NVIDIA 合计 118 个文件）在测试中被过度代表。
2. **|E| 以转换目录计数**，一个目录可能对应多个 pass，也可能一个 pass 覆盖多条路径；因此 |E| 是"接口数量"的代理，不是工作量的直接度量。
3. **`frontend` 层被系统性低估**：`torch` / `stablehlo` / `mhlo` 不在本仓库，导致"栈顶碎片化"的结论在本语料中只能被间接支持（由投入分布推断），不能被直接测量。要直接测量需并入 `torch-mlir` 与 `openxla` 的语料。
4. **层划分是主观的**（`layers.json`），且发现 2 已证明 5 层模型会把厂商内二级栈折叠掉。若换一种划分，H1/H2 的具体数值会变，但"端点收敛"与"投入不对称"两条定性结论应保持稳定——这一点建议做一次换划分重跑来确认，并在报告中如实写出。
