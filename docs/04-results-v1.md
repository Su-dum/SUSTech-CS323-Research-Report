## 发现 1｜收敛发生在「端点」，而不是「层」

**观察**

- 落到最深层的转换文件占全部层间转换的 **79.2%**（236 / 298）。
- 真正的汇聚点是少数**具体方言**：

| 目标方言 | 入度（文件数） |
|---|---|
| `llvm` | **104** |
| `rocdl` | 57 |
| `spirv` | 57 |
| `xevm` | 23 |
| `emitc` | 19 |
| `nvvm` | 19 |

- 汇入 `llvm` 的 104 个文件来自 **19 个不同方言**：`spirv`(25)、`func`(13)、`memref`(10)、`acc`(10)、`vector`(10)、`xevm`(6)、`arith`(5)、`arm_sme`(3)、`async`(3)、`complex`(3)、`cf`(3)、`gpu`(3)、`nvvm`(2)、`omp`(2)、`ptr`(2)、`index`(1)、`math`(1)、`mpi`(1)、`ub`(1)。

**解释**

MLIR 生态里确实存在"多方汇入同一点"的结构，但那个点是 **LLVM dialect**（其次 ROCDL / SPIR-V），不是某个抽象层。原因不难理解：`llvm` 方言下面直接就是 LLVM 后端，是所有目标里唯一"已经被全行业接受"的接口。

这修正了"分层共享"的直觉图像：共享不是**层与层之间**的对称交换，而是所有源都指向少数终端的**星形结构**。

**不能说明什么**：这不代表其他层没有价值——`linalg`、`scf`、`memref` 是**变换发生的场所**，只是不是**汇聚的场所**。两者是不同问题。

> 图 3（`fig1_layer_transitions.svg`）承载这条发现；`out/facts.md` §2 是数字版。

## 发现 2｜最深层内部有 114 个转换文件、8 条边：厂商内二级栈 + 出口转向

**观察**

| 转换 | 文件数 | 性质 |
|---|---|---|
| `amdgpu` → `rocdl` | 42 | 厂商内：AMD 高层 → 低层 |
| `spirv` → `llvm` | 25 | 跨厂商：通用 GPU 出口 → 通用 CPU 出口 |
| `xegpu` → `xevm` | 20 | 厂商内：Intel 高层 → 低层 |
| `acc` → `llvm` | 10 | 出口转向 |
| `nvgpu` → `nvvm` | 6 | 厂商内：NVIDIA 高层 → 低层 |
| `xevm` → `llvm` | 6 | 出口转向 |
| `arm_sme` → `llvm` | 3 | 出口转向 |
| `nvvm` → `llvm` | 2 | 出口转向 |

**解释**（两类现象要分开）

1. **厂商内二级栈**（`amdgpu→rocdl`、`xegpu→xevm`、`nvgpu→nvvm`）：每个厂商在 MLIR 里不是一层，而是**两级**——面向编程模型的一级 + 面向指令的一级。合计 **68 个文件 / 3 条边**。
2. **出口转向**（`spirv/acc/xevm/arm_sme/nvvm → llvm`）：各种高层目标方言最终再落回 `llvm`。合计 **46 个文件 / 5 条边**。

**⚠️ 归因必须谨慎**（外部 review 的正确批评）：厂商内二级栈只贡献 **3 条边**，**不是**"层对 15 → 方言对 76"膨胀的主因。主因是**层边界内部本身就含多个方言对**（例如 parallel→target 一条边界里就有 `gpu→{spirv,rocdl,nvvm}`、`scf→spirv`、`omp→llvm`）。

正确表述：

> 厂商内二级栈是 `|E|` 的一部分来源（3 条边 / 68 个文件），但 15→76 的膨胀主要来自**方言对粒度本身**：一条层边界内平均约含 5 个方言对。

这条让发现 2 从"因果论断"退回"结构性描述"，反而更结实：它说清了 `|E|` 为什么天然比层数大一个量级。

> 图 1 中五个"层内 N"小凸起即此发现；`out/facts.md` §3 下半张表是明细。

## 发现 3｜投入是「两级结构」，不是「四高均匀」——修正后重写

**观察**（`test/Dialect/<X>` 文件数，已归属 **1,390** 个）

| 层 | 文件数 | 占已归属 |
|---|---|---|
| 硬件目标层 | 364 | 26.2% |
| 张量代数/结构化计算层 | 354 | 25.5% |
| 并行与控制抽象层 | 235 | 16.9% |
| 存储与向量层 | 222 | 16.0% |
| 跨层通用方言（单列） | 73 | 5.3% |
| **框架/算子集导入层** | **62** | **4.5%** |
| 编译器基础设施方言（6 个，单列） | 80 | 5.8% |

**解释**

> **这是被 review 修正掉的一条**：v1 曾写"四个中后段层几乎均匀（20.6%–24.0%，差不到 4 个百分点）"——那是因为 `Dialect/SparseTensor`(122) 与 `Dialect/LLVMIR`(86) 被静默丢弃。补回后是**明显两级**：
>
> - 高档：目标层 26.2%、张量层 25.5%
> - 中档：并行层 16.9%、存储层 16.0%
> - 低档：导入层 4.5%

**仍然成立、而且更强的结论**：**导入层投入始终最低**，只有中后段的约 **1/4–1/6**（4.5% vs 16–26%）。原因不是上游不重视框架接入，而是承接框架的活在**别的仓库**：`torch-mlir` 接 PyTorch、`StableHLO` 接 JAX/TF、`ONNX-MLIR` 接 ONNX。本语料里 `frontend` 层作为转换源的方言**只有 `tosa` 一个**（实测 N = 1），`torch`/`stablehlo`/`mhlo` 一个都没有。

即：**共享与复用集中在中后段，栈顶由各生态自己承担**——主论点在修正后依然成立，且差距比原来更大。

**附带的新观察**：**编译器基础设施方言**（`transform` 45、`irdl` 16、`smt` 8、`dlti` 5、`pdl` 4、`pdl_interp` 2，共 80 个文件、5.8%）是独立一类投入——它们描述**编译过程本身**，不属于被编译程序的抽象层。把这批文件从"层"里分出去，本身就值得写进正文。

**不能说明什么**：投入 ≠ 难度 ≠ 价值。

## 发现 4｜「N×M 塌缩」有两种口径，答案相反

**观察**

| 口径 | 计数对象 | 数量 | p=0.6 时的 N\* |
|---|---|---|---|
| 架构级 | 层与层之间的非零边界 | **15** | **4.6** |
| 工程级 | 真正要写的 (源方言, 目标方言) 对 | **76** | **15.5** |

（`N* = (|E| + M) / (p·M − 1)`，**M = 11**，由数据自动实测：`target` 层内作为转换目标的方言，含 `llvm`/`spirv`/`rocdl`/`xevm`/`nvvm`/`amdgpu`/`xegpu`/`arm_sme`/`nvgpu`/`vcix`/`x86`。）

在 N = 8、M = 11 的现实规模下：

- 架构级：成对适配 **88**，分层共享 **69.2** → **分层占优**；
- 工程级：成对适配 **88**，分层共享 **130.2** → **分层反而更贵**。

**解释**

同一个命题，换个计数单位就从"成立"变成"不成立"。差别不在 p，而在于**你把什么算作"一次实现"**：

- 若"增加一层"等于把这一层写一遍，层边界只有 15 条，共享收益立刻兑现；
- 若"增加一层"意味着给这一层里每个方言对写一条转换，成本是 76，且随**硬件家族数**增长。

真实工程明显偏向工程级：`AMDGPUToROCDL` 与 `NVGPUToNVVM` 不可能因为"同在一层"就被同一段代码实现。

**改写成这个形式才站得住**：

> MLIR 把成本从 `N·M` 重写为 `|E| + N + M`。以层边界计数时门槛极低（N\* ≈ 4.6），以方言对计数时门槛升至约 15.5；两者之差就是"分层"这一抽象在工程实现中漏掉的成本。门槛对 p 高度敏感：p 从 1.0 降到 0.4，N\* 从 8.7 升到 25.6（约 2.9 倍）。

**敏感性数据**（M = 11）

| p | 0.4 | 0.5 | 0.6 | 0.8 | 1.0 |
|---|---|---|---|---|---|
| N\* | 25.6 | 19.3 | 15.5 | 11.2 | 8.7 |

## 发现 4b｜`|E|` 的社区摊销（外部 review 建议，最有价值的一条）

上面的模型把 `|E|` 当作**单个组织**要支付的成本。但在 MLIR 生态里，`|E|` 是**上游/社区实现一次、所有采用者共享**的：

- 单组织视角：`C_layer = |E| + N + M` —— 于是 N 不够大时分层更贵（工程级门槛 ≈15.5 由此而来）；
- 生态视角：`|E|` 由社区一次性支付，**每个采用者只付边际成本 N + M**。

这解开了一个张力：**"本文模型说分层更贵"与"MLIR 确实被广泛采纳"并不矛盾**——采纳者摊销的正是 `|E|`。也解释了为什么共享层一旦形成就极难被替代（沉没成本由生态承担），以及为什么**另起**共享层比**加入**它贵得多。

写法提醒：这一段**不是本文的测量结果，而是对模型的补充解释**，正文要明确标注，否则会变成新的过度声明。

## 发现 5｜`func` / `arith` 是唯一的真·跨层通用语

**观察**（共现矩阵，`out/fig2_dialect_cooccurrence.svg`）

- `func` 与 `arith` 的共现文件数 **1,454**，各自与 `memref`(609/562)、`vector`(479/437)、`linalg`(452/379)、`scf`(449/421)、`tensor`(398/353) 的共现都在数百量级。
- `transform` 与 `linalg`(154)、`tensor`(99)、`scf`(62) 的共现显著高于其他，与 `llvm` 只有 4。
- `llvm` 与 `omp` 共现 **234**，是它除 `func`/`arith` 外最高的一个。

**解释**

`func`/`arith` 与几乎所有层共现，印证"跨层通用语"地位；本实验把它们单列 `crosslayer`（73 个文件、5.3%）是对的。`transform` 几乎只与结构化计算层共现 → 调度 DSL **依附于** `linalg`/`tensor`。`llvm`↔`omp` 的高共现来自 `OpenMPToLLVM`。

**不能说明什么**：共现高不等于依赖强；文件粒度不均会放大数值。

## 稳健性检验｜换一套层划分

把「硬件目标层」拆成 **通用出口层**（`llvm`、`spirv`）+ **厂商指令方言层**（`rocdl`/`amdgpu`/`nvvm`/`nvgpu`/`xegpu`/`xevm`/`arm_*`/`x86`/`wasmssa`/`acc`/`vcix`），5 → 6 层。`tools/layers_alt.json` 由 [tools/make_layers_alt.py](../tools/make_layers_alt.py) 从主配置生成，保证 aliases/noise/overrides 不漂移。

| 量 | 主划分（5 层） | 替代划分（6 层） | 结论 |
|---|---|---|---|
| 方言对 \|E\| | 76 | **76** | **完全不变** |
| 非零层对 | 15 | **20** | 变 |
| 架构级 N\*（p=0.6, M=11） | 4.6 | **5.5** | 小幅变 |
| 工程级 N\*（p=0.6, M=11） | 15.5 | **15.5** | **完全不变** |
| "落到最深层"占比 | 79.2%（target） | **36.6%**（vendor） | **大幅变**（划分依赖） |
| 四层级投入 | 364/354/235/222 | 同 | 不变 |
| frontend 投入 | 62（4.5%） | 同 | 不变 |
| 入度最高的单一方言 | `llvm` 104 | `llvm` 104 | 不变 |

**怎么用**：

- 发现 4 的核心量（`|E| = 76`、工程级 N\* = 15.5）**与层划分无关**，可直接写进正文；
- "79.2% 落到最深层"**依赖把 target 划成一层**（换划分掉到 36.6%），正文**不要单独引用**；
- 发现 2 在替代划分里显式表现为 `vendor→vendor` 与 `vendor→generic_exit`，与主划分下"最深层内部 114 个文件"互为印证。

## 对命题的净修正（三条）

1. **"共享层"应改为"共享端点"**：收敛点是 `llvm`（104 个文件 / 19 个来源）、`rocdl`、`spirv`——是点不是层。
2. **"每层一次实现"应改为"每个方言对一次实现"**：以层边界计数只有 15，以方言对计数是 76，差一个量级，后者才是工程现实。
3. **门槛既取决于 p，也取决于谁支付 `|E|`**：单组织支付时 ≈15.5 个前端；社区摊销时门槛塌到 N + M 量级（发现 4b）。

## 必须写进局限的（四条，已按 review 修正）

1. **语料是上游测试集**，反映"上游认为需要覆盖什么"，不等于工业使用分布。`Integration/*` 有 423 个文件（12.7%），以 GPU 端到端为主。
2. **目标端分布不均**：入矩阵文件的目标家族分布为——通用 CPU 101、AMD 65、通用 GPU 57、Intel 33、NVIDIA 21、C/C++ 19、Arm 3（合计 **299**；另有 72 个落在中间层目标：`scf` 13、`cf` 12、`linalg` 8、`gpu` 6 等）。GPU 厂商合计 **119**（AMD 65 + Intel 33 + NVIDIA 21），被过度代表。
3. **`|E|` 是接口数量的代理**：76 条方言对按等权计，忽略难度差异；且它是**下界**（81 个转换文件因一端方言不定被排除）。
4. **层划分主观**：非零层对 15 vs 20；最深层占比 79.2% vs 36.6%。已做稳健性检验，正文只用划分不变量。
