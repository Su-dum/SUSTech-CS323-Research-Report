# §6 素材：代价、局限与结论强度分级

> 这一节不是"免责声明"。它的任务有两个：
> ① 说清 MLIR 这套设计的**代价**（机制层面的，不是本文方法的）；
> ② 说清本文证据**能支撑到哪一步**，并把结论按强度分级。
>
> 全部数字的唯一真源是 [out/facts.md](../out/facts.md)（脚本生成）。本文改动数字后必须重新生成并核对。

---

## 1. §6.1 机制层面的代价（MLIR 自身的设计代价）

这四条不是本文发现的，但必须由本文**承认**——否则 §3 的赞美会显得单薄。

### 代价 1｜栈顶仍然碎片化，共享主要发生在中后段

**证据**（本文实测）：框架/算子集导入层的测试投入只占已归属文件 **5.2%**（56/1,077），是四个中后段层的约四分之一（20.6%–24.0%）。且上游语料里 `frontend` 层作为转换源的方言只有 `tosa` 一个，`torch` / `stablehlo` / `mhlo` **一个都没出现**。

**正确解读**：这不是说那些方言不存在，而是说它们**在别的仓库**（`torch-mlir`、`openxla/stablehlo`、`onnx-mlir`）。共享没有发生在栈顶——栈顶由各生态自己承担。

**不要过度解读**：不能说"MLIR 没有解决框架接入问题"，只能说"MOLIR 的共享收益在栈顶由外部仓库实现"。

### 代价 2｜抽象泄漏集中在三处：bufferization、shape、量化

- **bufferization**：从值语义（`tensor`）到缓冲区语义（`memref`）不是语法改写，而要决定每次 read/write 是 copy 还是 in-place。这是**语义决策**，不是降级规则，所以最容易在层边界上出错。
- **shape 推断**：动态 shape 需要 witness/约束的传播机制，这部分语义横跨 `shape` / `tensor` / `memref` 三层。
- **量化**：`quant` 层与 `arith`/`linalg` 的类型系统对齐需要额外表示（scale/zero-point 的归属）。

**写法**：不要给数字，写机制 + 一句"这类信息在层边界上无法被完全抽象掉，因此每增加一层都会增加一处潜在的语义错位点"。可引 MLIR 的 [Bufferization](https://mlir.llvm.org/docs/Bufferization/) 与 [Shape Inference](https://mlir.llvm.org/docs/ShapeInference/) 文档。

### 代价 3｜pass 链变长，调试面变大

**可得证据**（本文实测）：3,309 个测试文件含 `// RUN:` 行，其中只有 **356 个（10.8%）** 使用 `-pass-pipeline`。也就是说上游语料**以单 pass / 单转换的测试为主**。

**这条证据有两种用法，注意别混**：
- 用于**方法局限**：本语料适合衡量"转换接口的数量"，**不适合**衡量"完整流水线的开销"；
- 用于**代价讨论**：要说明"多级 IR 使 pass 链变长、调试变难"，就必须承认**本文没有测量这个成本**——它只能作为机制层面的定性判断。

**不要写**："多级 IR 导致编译时间增加 X%"——本文没有任何编译时间数据。

### 代价 4｜共享层的治理成本

**证据**（见 [07-section5-stablehlo.md](07-section5-stablehlo.md)）：StableHLO 为把"一层"变成各方敢依赖的契约，付出的成本包括——5 个兼容性 RFC、每周一次的发布节奏、一个专门用于版本化的 `VHLO` 方言、逐 PR 的双向兼容测试、以及一份写明 out-of-scope 的文档。

**这条是本节最有力的一条**，因为它把"治理成本"从修辞变成了可枚举的工程产物，而且**这部分成本不体现在 `|E|` 里**。

## 2. §6.2 本实证的局限（逐条对应到结论）

| # | 局限 | 具体证据 | 削弱了哪个结论 | 正文怎么处理 |
|---|---|---|---|---|
| L1 | **语料是上游测试集**，反映"上游认为需要覆盖什么"，不等于工业使用分布 | 3,329 个文件；其中 `Integration/*` 有 **423 个（12.7%）**，以 GPU 端到端测试为主 | 所有"投入分布"类结论（发现 3） | 在方法段与 L1 明确写出；结论限定为"结构性"而非"使用率" |
| L2 | **目标端分布不均**，GPU 厂商被过度代表 | 371 个入矩阵文件的目标家族：通用 CPU 101（27.2%）、AMD 65（17.5%）、通用 GPU 57（15.4%）、Intel 33（8.9%）、NVIDIA 21（5.7%）、C/C++ 19（5.1%）、Arm 3（0.8%） | 发现 1、发现 2 的**外推**（"收敛在 LLVM"可能部分反映上游测试重心在 GPU 后端） | 明确写"以 GPU 后端为主的测试重心"这一偏差；把"收敛在 `llvm`"表述为**上游语料中的**收敛，而非全行业 |
| L3 | **`\|E\|` 是接口数量的代理，不是工作量** | 78 条方言对；一条 `Conversion/XToY` 目录可能对应多个 pass 组合（如 `GPUCommon`、`LLVMCommon` 是工具集合而非单一转换） | 发现 4 的**成本量级** | 明写"等权假设"：把每条边视为等成本，忽略难度差异；因此结论是**结构性**的 |
| L4 | **口径偏差：`builtin` 被显著低估**；另有 81 个转换文件未入层间矩阵 | `module` 在文本 IR 中写作无命名空间的 `module`，故 `builtin` 仅计得 101 个算子；81 个文件因一端方言不定被排除 | 共现矩阵中 `builtin` 的行/列；`\|E\|` 的**完备性** | 明写"`\|E\| = 78` 是**下界**"——真实值只会更大，工程级门槛只会更不利 |
| L5 | **层划分是主观的** | 主划分 14 个非零层对、替代划分 18 个；"落到最深层"的占比 79.0% → 36.4%；架构级 N\* 4.8 → 4.3 | 一切以"层"为单位的百分比 | 已做稳健性检验（`tools/layers_alt.json`）；正文只用**划分不变量**（方言级数字） |
| L6 | **只用一个仓库** | 未纳入 `torch-mlir`、`openxla/stablehlo`、`onnx-mlir` 的语料 | 发现 3 的"栈顶碎片化"只能**间接**推断 | 明写这是间接证据；作为 future work |
| L7 | **参数来源不对称** | M = 10 由数据实测（target 层内作为目标的方言）；N = 8 是生态假设；p 只做敏感性分析 | 发现 4 的 N\* 具体数值 | 明写三者的来源差异；强调结论**不依赖** p 的具体取值，而依赖"p 变化时门槛变化 2.3 倍" |

> 排序建议：正文按 **L1 → L4 → L5 → L6** 的顺序写（从最实质的到最技术性的），L2/L3/L7 可并入相应句子。L5 必须有，因为它证明你**自己**做过证伪。

## 3. §6.3 结论强度分级（写正文时按这张表取词）

### 硬结论：方言级，与层划分无关，可以直接断言

| 结论 | 数字 |
|---|---|
| 上游语料中不同方言对转换的数量（**下界**） | **78** 条，覆盖 452 个 Conversion 文件中的 371 个 |
| 汇入 `llvm` 的转换文件数 / 来源方言数 | **101** 个文件，来自 **18** 个方言 |
| 目标层内部的转换规模 | **114** 个文件 / 8 条边 |
| 厂商内二级栈 | `amdgpu→rocdl` 42、`xegpu→xevm` 20、`nvgpu→nvvm` 6，共 68 |
| 导入层投入占比 | **5.2%**（56/1,077） |

### 软结论：依赖参数或划分，必须带条件说

| 结论 | 依赖 | 写法 |
|---|---|---|
| 工程级门槛 N\* ≈ 17.6 | M = 10、p = 0.6 | "在 M = 10、p = 0.6 下约 18 个前端" |
| 架构级门槛 N\* ≈ 4.8 | 层划分 | "以层边界计数时约 5 个前端" |
| 79.0% 落到最深层 | 把 target 划成一层 | **建议不用**；改用方言级表述 |
| p 敏感度 2.3 倍 | N、M 固定 | "在本文参数下约 2.3 倍" |

### 禁止说的（一写就被抓）

- ❌ 任何性能 / 编译时间 / 使用率数字（本文没有测）
- ❌ "MLIR 解决了 N×M 问题"
- ❌ "79% 的转换落到硬件目标层"（单独引用时，见 L5）
- ❌ "Triton 绕开了 MLIR"（它是 MLIR 上的一组 dialect）
- ❌ "MHLO 被淘汰是因为设计不好"（官方措辞是 deprecated + 迁移建议）
- ❌ "MLIR 提供兼容性保证"（那是 StableHLO 建立的，见 07 推论 B）

## 4. §6.4 写法建议（约 1.5 页，四段）

| 段 | 内容 | 篇幅 |
|---|---|---|
| 1 | **代价是设计的一部分**：碎片化仍在栈顶（5.2%）、抽象泄漏集中在 bufferization/shape/量化、治理成本可枚举（引 §5）。开篇一句立住"本文不把 MLIR 当归宿" | 0.5 页 |
| 2 | **证据的边界**：语料代表性（L1/L2）、代理指标（L3）、口径偏差与下界（L4）。给出 `|E| = 78` 是下界这一条，因为它**反而加强了**结论的方向 | 0.4 页 |
| 3 | **结论的边界**：层划分主观性 + 已做稳健性检验（L5）；单仓库（L6）；参数来源（L7）。收在一句"因此本文的结论是结构性的，不是绝对成本的" | 0.4 页 |
| 4 | **一句自我定位**（建议原话）："本文能支持的最强主张是：MLIR 把适配成本的组织方式从成对定制改为分层共享，并在上游语料中呈现出以 `llvm` 为端点的收敛；本文不能支持的是：这一转变在具体硬件上更快，或已被多数框架采纳。" | 0.2 页 |

> 第 4 段的写法值得学：**主动把"能支持"和"不能支持"并列**，比只写"本文有局限"有力得多，而且直接回应了"你是不是在吹 MLIR"这个潜在质疑。

## 5. §6.5 不要写成什么

- ❌ 不要把 §6 写成罗列式的"局限性说明"（"由于时间有限……"）。每一条都要**绑定到具体结论**：削弱哪一条、削弱多少。
- ❌ 不要用"可能存在偏差"这种空话，要给数字或机制。
- ❌ 不要把所有局限都推给"时间不够"——L1/L2/L3 是**设计选择**（选了测试语料而非生产 trace），不是时间问题。承认是选择，比承认是仓促更体面。
- ❌ 不要在 §6 里新提出未经检验的说法。这一节只做**收缩**，不做扩张。

## 7. 与 §4 的分工（避免重复）

- **§4 讲"发现了什么"**：五条发现 + 稳健性检验，语气是陈述。
- **§6 讲"这些发现能撑多远"**：代价 + 局限 + 强度分级，语气是收缩。

同一个数字（如 78 条边）在 §4 出现是**证据**，在 §6 出现是**下界**——措辞要区分，否则读者会觉得你在反复强调同一个数。
